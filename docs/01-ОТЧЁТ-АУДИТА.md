## 2. Аудит безопасности

### Исправлено в этом аудите

| # | Проблема | Риск | Исправление |
|---|----------|------|-------------|
| S1 | Сравнение подписи Click через `===` | Timing attack на платёжный callback | `timingSafeEqual` |
| S2 | Проверка Payme-авторизации `password === key` | Timing attack на merchant API | `timingSafeEqual` по SHA-256-хэшам |
| S3 | CORS пропускал **любой** `*.onrender.com` origin | Любой чужой сайт на Render мог вызывать API с cookies пользователя | Только точный список origin |
| S4 | OTP: не было rate limit и cooldown (ТЗ §7) | SMS-флуд, перебор | 5 запросов/час на телефон, cooldown 60 сек, максимум 5 попыток ввода (было), фиксированный код `123456` только вне `APP_ENV=production` |
| S5 | Payme `GetStatement` всегда возвращал пустой массив (ТЗ §29) | Нарушение контракта Payme | Реализован вывод реальных транзакций за период |

### Что проверено и в порядке

- Секретов в Git нет: `.env` не коммитится, `.gitignore` корректен, в репозитории только `.env.example`.
- Токены сессий хранятся как SHA-256 хэши (`Session.tokenHash`), OTP — как хэши (`codeHash`).
- AliExpress refresh/access токены зашифрованы AES-256-GCM, ключ из env, проверка setup-секрета через `timingSafeEqual`.
- Payme: сумма сверяется с заказом на backend (`order.totalMinor * 100`), а не доверяется клиенту; Click: проверка merchant/amount/дубликата callback есть.
- Firebase: требуется `email_verified`, конфликты привязки аккаунтов обрабатываются.
- Сессии имеют срок действия (30 дней), logout удаляет сессию.
- SQL-инъекции: Prisma, параметризованные запросы.
- ValidationPipe с `whitelist: true, forbidNonWhitelisted: true` включён глобально.

## 3. Дыры по ТЗ, которые НЕ закрыты этим аудитом (требуют разработки)

1. **PDD-адаптер отсутствует** (ТЗ §9–13): нет `PddAdapter`, `GET /integrations/pdd/status`, кэша Redis, маппинга ошибок `PDD_*`. В ТЗ продукт называется Pinduoduo, фактически интегрирован AliExpress — нужно решение владельца: либо PDD API (нужен официальный доступ), либо переименование потоков.
2. **Checkout preview** (ТЗ §21): `POST /checkout` возвращает `410 Gone`, заказ создаётся через `POST /orders`, но нет `GET /checkout/preview` с расчётом доставки/комиссии/скидки до создания заказа.
3. **Idempotency-Key на создание заказа** (ТЗ §24) не реализован — двойной клик создаст два заказа.
4. **Модель Address** (ТЗ §22) отсутствует — адрес передаётся строкой в заказе.
5. **Единая модель товара** (ТЗ §14): нет `source` (`LOCAL`/`PDD`) и `externalId` в `Product`; marketplace-товары upsert-ятся с клиентским `productId` — см. также риск подмены ID.
6. **Запуск платежа из checkout**: заказ создаётся в `AWAITING_PAYMENT`, но покупательский `POST /payments` → `paymentUrl` не предоставлен (подтверждает вывод плана: «реальный checkout не открывать»).
7. **Paynet**: базовый каркас есть, `PerformTransaction` и боевой контур требуют merchant-договора и тестов.
8. **DeliveryAdapter/Cainiao**: только контракт и таблицы, live-клиента нет (ТЗ §33).
9. **Тесты отсутствуют полностью** (ТЗ §46–47): папка `tests/` пустая, нет jest-конфига, нет E2E.
10. **Swagger/OpenAPI** (ТЗ §42) не подключён.
11. **Frontend-монолит**: `App.tsx` — 2211 строк, структура ТЗ §4 (app/components/features/pages/services) не внедрена; кнопки и состояния loading/error проверены не все (ТЗ §38).
12. **Роутинг** (ТЗ §37): SPA без react-router, страницы `/orders/:id`, 404 — частично через внутреннее состояние.
13. **CRM хранит токен в localStorage** и не имеет refresh-механики.
14. **Healthcheck в docker-compose** (ТЗ §48) отсутствует; backend в compose не поднимается.
15. **CI tests**: prisma validate добавлен в CI в патче `uriona-fixes.patch` (прямой push workflow-файла недоступен из-за ограничения токена).
